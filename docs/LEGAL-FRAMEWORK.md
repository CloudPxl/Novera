What was recorded instead of changed, and why:

- **Retention after erasure.** The memo says billing records (5–10 years, Law 82/1991) and acceptance
  records (contract evidence) outlive an erasure. `erase_workspace()` deletes both today. Keeping them
  changes a guarantee, so the database is unchanged; the gap, the tables and a migration shape are in
  the counsel file ("Retention gap"), the retention schedule and the readiness page.
- **Reverse-charge invoice wording.** The billing code has a hook (the Stripe customer's invoice
  settings), but applying "Reverse charge" on a VAT number Novera has not validated is the VIES
  question itself. It stays a pre-live task for the accountant (`docs/BILLING-DECISIONS.md`, section 4).
- **Report terminology.** Not renamed: customer surfaces already say "agent evaluation report", and the
  only "conformity assessment" is the notice that a report is not one. See the Terminology section.

| Certified / compliant / approved by a regulator | Never used about an agent or report. The report language rule (`src/lib/report/language.ts`) and the legal tests refuse them | — |
| "Approved" | Only about a person's decision: an approved draft, an approved policy version, a support reply | — |

The report page has said "Agent evaluation report" since Phase 7. `CLAUDE.md` still calls the
product a "conformity report" internally. That is orientation, not customer copy, and it is not shown
to anyone.

The founder's memo (2026-10-16) asks to purge "conformity assessment" in favour of "Evaluation Evidence
Report". Checked on 2026-10-16: no customer-facing string names Novera's output a "conformity report",
"compliance report" or "certificate". "Conformity assessment" appears only in the notice that a report
is *not* one, which stays. The established phrase "agent evaluation report" is kept rather than adding
a third name. The one remaining use is the sealed name of the built-in suite eu-support v1–v5, "EU
support agent conformity suite"; renaming it needs a new suite version and is listed for counsel
(question 39).

## Billing configuration (§20.3), as found 2026-10-13

- **Fixed:** the price variables have the names the code reads, `STRIPE_PRICE_TEAM_BYOK` and
  `STRIPE_PRICE_AGENCY_PRO`, in Production and Preview.
- **Found:** `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` are set in **Production** as well as
  Preview, and production billing was active in Stripe *test* mode. Anyone could have subscribed
  with a test card and, since D3, run on a paid plan for free. A production deployment now refuses
  a test key (`billingConfig`), whatever the environment holds. **David:** delete both, and the two
  price variables, from Production. Keep them in Preview only, and point the sandbox webhook at a
  Preview deployment with a protection bypass.
