## Confirmed bugs

### C1 · High · The migration ledger is writable with the public anon key

- **Classification:** CONFIRMED. Isolated stack: every step below. Production: the catalog on 2026-09-30
  (RLS off; `anon` and `authenticated` hold DELETE, INSERT, SELECT, TRUNCATE, UPDATE). Today's read-only
  re-check was refused by the session's permission classifier.
- **Where:** `scripts/migrate.mts:36-42` creates `novera_migrations` with no RLS and default grants.
  `:47-50` trusts it, and `:72-75` skips any file whose name and checksum match a row.
- **Invariant:** the schema is what `supabase/migrations/` says. Every guarantee in CLAUDE.md is a migration.
- **Reproduction:** `node --conditions=react-server --env-file=.env.local harness/ledger.mts`.
- **Actual:**
  - Through PostgREST, `anon` and `authenticated` each got SELECT 200 (44 rows), INSERT 201, UPDATE 200 and DELETE 200.
  - A row forged with the anon key for a new migration, carrying its correct checksum (`sha256(file)[:16]`, computable by anyone because the repo is public), made `migrate` exit 0 with "0 migration(s) applied". **The migration never ran, and nothing said so.**
  - A wrong checksum gave "CHANGED … already applied with a different checksum", which blames the wrong cause.
  - A deleted row made the migration run again.
- **Expected:** no client role can see or change the ledger, and a migration can be skipped only by the migration runner itself.
- **Impact:** anyone holding the anon key, which ships in every browser bundle, can make the *next* security migration silently not apply. That includes the fix for this finding, once it is pushed. They can also re-run old migrations, or TRUNCATE the history.
- **Minimal fix:**
  1. Migration 0045: `alter table novera_migrations enable row level security; revoke all on novera_migrations from public, anon, authenticated;`.
  2. `migrate.mts` runs the same two statements **before it reads the ledger**, every time, so hardening never depends on the ledger it protects.
  3. `migrate.mts` takes `pg_advisory_lock` for the whole run.
  4. `migrate.mts` reports "skipped, recorded but not applied by this runner" separately from "CHANGED".
- **Regression test:** extend `verify:db`. As `anon` and `authenticated`, SELECT, INSERT, UPDATE and DELETE through PostgREST must each be refused. The service role and the migration role can still run. A forged row is impossible.
- **Migration impact:** one additive migration. The service role and `postgres` bypass RLS, so `migrate`, `verify:*` and the app are unaffected.
- **Rollback:** `alter table novera_migrations disable row level security;` plus the original grants. Not recommended.
- **External configuration:** run the two statements in production first (SQL editor or `npm run migrate`), then confirm through the catalog that RLS is on and the grants are gone, **before pushing anything that names the fix**.

### C6 · Medium · Quadratic redaction and unbounded agent replies block the server

- **Classification:** CONFIRMED locally. On Vercel the per-instance and cross-request effect is UNTESTED.
- **Where:**
  - `src/lib/redact/pii.ts:52`, the EMAIL pattern `/[A-Za-z0-9._%+-]+@…/g`, which has no left boundary. On a long run of those characters with no `@`, every start position scans to the end.
  - Called on report sealing (`src/lib/report/build.ts:113`) and on provider redaction (`src/lib/privacy/data-class.ts:87`).
  - `src/lib/agents/http.ts:126` reads the whole body with no size limit.
- **Invariant:** a slice hands back inside the platform limit, and one customer's input cannot take the service down.
- **Reproduction:**
  - `harness/hot.mts` and `hot2.mts`: `redact()` on a long unbroken token.
  - `harness/agent-modes.mts` mode `/big-reply?mb=20`.
- **Actual:**
  - EMAIL pattern alone: 64 KB of hex 6.9 s; 64 KB base64url 6.8 s; 64 KB of one letter 6.9 s; 128 KB 27.3 s. Ordinary prose is not affected.
  - A 20 MB readable reply kept `/execute` busy for more than 300 s, until the harness's HTTP client gave up. The `next-server` process then stayed at 100% CPU and **answered no request** (`GET /` timed out after 10 s) until it was killed.
  - Which call in the slice reached `redact()` was not profiled in-process.
- **Expected:** `redact()` is linear, and replies above a stated limit are refused or truncated, with that recorded as evidence.
- **Impact:**
  - An agent that returns a base64 attachment or a long hash dump (realistic) costs seconds to minutes per redaction pass.
  - On Vercel (inferred, UNTESTED) the slice would be killed at 60 s, retried after its lease, and killed again, so the run never finishes and stalls out after 24 hours.
  - If an instance serves concurrent requests (Fluid compute), other requests on it would wait too (UNTESTED).
- **Minimal fix:**
  1. Bound the local part to `[A-Za-z0-9._%+-]{1,64}`, and add a lookbehind `(?<![A-Za-z0-9._%+-])` so only the start of a run attempts a match.
  2. Audit the other patterns the same way.
  3. Cap the agent body at 256 KB by streaming and stopping at the cap. Record "reply exceeded 256 KB" as a no-result with the size, never truncated text passed off as the reply.
  4. Apply the same cap to read-back bodies.
- **Regression test:** a unit test that 1 MB of `[A-Za-z0-9]` redacts in under 200 ms and still finds an email at its end; a responder test that a 20 MB body yields a recorded no-result within one slice.
- **Migration impact:** none.
- **Rollback:** revert the commit.
- **External configuration:** none. The limit is customer-facing behaviour, so it goes in the docs.

### C5 · Medium · A stalled reply body aborts the whole run

- **Classification:** CONFIRMED.
- **Where:**
  - `src/lib/agents/http.ts:126`: `await response.text()` sits outside the `try` that handles the timeout. The fetch resolves on headers, and the timeout then fires during the body read.
  - `src/lib/runner/execute.ts:255`: `agent.send` is not caught per case.
  - `execute.ts:627-632` turns the throw into `aborted`, and `src/lib/workflow/start-run.ts:204-207` writes it.
- **Invariant:** a case that fails is recorded as a case, and one bad case does not destroy the run's evidence.
- **Reproduction:** `harness/agent-modes.mts`, modes `/stall-body` and `/stall-first`.
- **Actual:**
  - `/stall-body` (one scenario): run `aborted`, "The operation was aborted due to timeout", 0 rows.
  - `/stall-first` (the first of six stalls; the rest answer in 1.5 s): run `aborted`. 5 rows were saved but no report can ever be sealed.
  - For contrast, a connection that never sends headers (`/hang`) is handled correctly: "The agent did not answer within 5 s", recorded as a no-result case.
- **Expected:** the stalled scenario is a no-result case ("the agent's reply did not finish within N s"), and the run completes and seals with the gap shown.
- **Impact:** a flaky network or a slow-streaming agent turns a run into nothing, and the customer reruns and pays again.
- **Minimal fix:** move the body read inside the `try` with the same deadline, and wrap `agent.send` per case so that any adapter exception becomes an `error` case carrying its message.
- **Regression test:** a responder test for `/stall-body` and `/stall-first`: the run completes, 6 rows, 1 no-result with the timeout reason.
- **Migration impact:** none. **Rollback:** revert. **External configuration:** none.

### C7 · Medium · The trial cap can be exceeded by concurrent starts

- **Classification:** CONFIRMED.
- **Where:** `src/lib/auth/entitlement.ts:47-52` counts the workspace's runs and `:79` compares the count with 3. `src/lib/workflow/start-run.ts:81-103` inserts afterwards, with no lock between the two.
- **Invariant:** the trial is capped at three runs on Novera's own keys. This is customer-facing: "After three runs, connect your own model key" (`data/docs/the-trial-and-your-own-key.md:7`).
- **Reproduction:** `harness/idem.mts`, 20 concurrent `POST /api/v1/runs` per fresh trial workspace, three trials.
- **Actual:** 7, 14 and 17 runs created (201 responses), against a limit of 3.
- **Expected:** exactly 3 created and 17 refused, whatever the concurrency.
- **Impact:** anyone with a `run` key, or several browser tabs, can spend Novera's shared free-tier grading quota without limit. That degrades every other trial's verdicts, the failure mode 0041 was written to prevent.
- **Minimal fix:** enforce the cap in Postgres. Either a `before insert` trigger on `runs` that takes `pg_advisory_xact_lock(hashtext(workspace_id))` and refuses a trial-funded insert past 3, or a `start_run` RPC that does the count and the insert in one transaction under that lock. Keep the app check for its sentence.
- **Regression test:** `verify:byok` gains "20 concurrent starts on a fresh trial → exactly 3 runs".
- **Migration impact:** one migration (a function and a trigger).
- **Rollback:** drop the trigger.
- **External configuration:** none.

### C2 · Medium · One webhook delivery can be POSTed several times

- **Classification:** CONFIRMED.
- **Where:** `src/lib/webhooks/deliver.ts:71-81` selects pending rows with no claim, and `:107` sends.
- **Invariant:** CLAUDE.md "announces a run once"; `data/docs/api.md:73` "Each run is announced once".
- **Reproduction:** `harness/race.mts`, parts C1 and C3.
- **Actual:** five concurrent `deliverDue` calls on one queued delivery made 5 POSTs with the same `Novera-Delivery` id. An immediate attempt overlapping one clock sweep delivered twice in **20 of 20** trials.
- **Expected:** one claim per attempt. Delivery is at-least-once (a receiver that accepts and the recording fails can see a repeat), and receivers deduplicate on `Novera-Delivery`.
- **Impact:** a receiver that does not deduplicate opens duplicate tickets or runs duplicate release gates.
- **Minimal fix:** migration 0047 adds `lease_token uuid` and `lease_until timestamptz`. The claim is one conditional `update … set lease_token = $t, lease_until = now() + 30 s, attempts = attempts + 1 where id = $id and status = 'pending' and next_attempt_at <= now() and (lease_until is null or lease_until < now()) returning *`. Every completion update includes `and lease_token = $t`. The send happens only if the claim returned a row.
- **Regression test:**
  - 20 concurrent deliverers on one row, with receivers answering 2xx, 500, a timeout, and accept-then-crash;
  - an immediate attempt overlapping a sweep;
  - an endpoint revoked while a delivery is leased;
  - in every case `attempts` equals the number of POSTs, and the body and signature are unchanged.
- **Migration impact:** additive columns and an index. 0042's frozen-field trigger must allow `lease_*` to move.
- **Rollback:** the columns are harmless if the code reverts.
- **External configuration:** none. The docs sentence G2 changes with it.

### C3 · Medium · Concurrent failed deliveries lose attempt counts

- **Classification:** CONFIRMED.
- **Where:** `src/lib/webhooks/deliver.ts:86-92`: `attempts` is computed from the value read, then written back.
- **Invariant:** every attempt is counted (0042), and backoff follows attempts.
- **Reproduction:** `harness/race.mts`, part C2.
- **Actual:** with the receiver answering 500 and five concurrent senders, 5 POSTs were made and the row records `attempts = 1`.
- **Expected:** `attempts = 5`, or one POST.
- **Fix, test, migration, rollback:** the same as C2 (`attempts = attempts + 1` in the claim).

### C8 · Medium · One undecryptable endpoint stops every workspace's webhook deliveries

- **Classification:** CONFIRMED (the state was planted: an endpoint sealed under another key, which is what rotating `NOVERA_ENCRYPTION_KEY` leaves behind).
- **Where:** `src/lib/webhooks/deliver.ts:105`: `open(…)` sits outside the per-delivery `try`. The sweep (`:71-81`) covers every workspace, ordered by `next_attempt_at`.
- **Invariant:** one tenant's broken row cannot affect another tenant.
- **Reproduction:** `harness/poison.mts`.
- **Actual:** three sweeps each threw "Unsupported state or unable to authenticate data". A healthy delivery queued after the bad one was never sent; both rows stayed `pending/0`. The bad row's `next_attempt_at` never moves, so the block is permanent.
- **Expected:** the bad row fails with a reason, and the sweep continues.
- **Minimal fix:** move `open()` inside the `try` and record "the signing secret could not be opened" as a failure for that row only.
- **Regression test:** the poison test as a verifier; the healthy row is delivered in the same sweep.
- **Migration impact:** none. **External configuration:** none.

### C4 · Medium · A run-lease takeover re-sends scenarios and aborts the run

- **Classification:** CONFIRMED. The precondition is a slice still alive after its 70 s lease. On Vercel the 60 s kill normally prevents that, but a database call with no client timeout, a raised `maxDuration` or self-hosting does not.
- **Where:**
  - `src/lib/workflow/start-run.ts:190` releases the lease without checking who holds it.
  - `:204-207` aborts without checking who holds the lease.
  - `src/lib/store/supabase-run-store.ts:64` throws on the duplicate row.
  - `src/lib/runner/execute.ts:627-632` aborts the run.
- **Invariant:**
  - one writer per run;
  - a scenario is sent to the customer's agent once per run;
  - an aborted run is never sealed, so the abort loses the run's evidence.
- **Reproduction:** `harness/race.mts`, parts A, B and B2. A counting agent takes 6 s per reply; the lease is expired while slice A works; slice B claims.
- **Actual:**
  - A: 20 simultaneous `execute` calls started exactly 1 slice. The claim is atomic.
  - B: 9 agent calls for 6 scenarios (3 sent twice). Both slices ended `aborted` with "duplicate key value violates unique constraint run_cases_run_id_case_id_key". No report.
  - B2: the slice that had lost the lease still set `lease_until = null`.
- **Expected:**
  - a slice that has lost its lease sends nothing more;
  - release and abort apply only to the holder's own lease;
  - a duplicate row is treated as "already recorded" only when the stored row is for the same run and case.
- **Minimal fix:**
  1. Migration: `runs.lease_token uuid`.
  2. `claim_run_slice` writes a fresh token and returns it.
  3. Release and abort use `where lease_token = $mine`.
  4. The worker re-checks the token before each agent call.
  5. `saveCase` maps 23505 on `(run_id, case_id)` to "already recorded" after reading the row back.
- **Regression test:** race parts B and B2 as a verifier: no scenario sent twice, the run completes, a stale release changes nothing, a stale abort changes nothing.
- **Migration impact:** a column, plus a new version of `claim_run_slice` (same signature, returning the token).
- **Rollback:** the old function body.
- **External configuration:** none.

## Confirmed configuration hazard

### R1 · Medium · Without pg_cron, retention and stalled-run jobs silently do not exist

- **Classification:** CONFIRMED in a fresh environment; production is unaffected (4 jobs active and succeeding on 2026-09-30).
- **Where:**
  - `0037:143`, `0038:129` and `0040:44` schedule only `if exists (pg_cron)`.
  - The tick job (`novera-schedule-tick`) is installed by `npm run schedules:clock -- install`, never by a migration. Scheduled runs and webhook retries depend on it.
- **Invariant:** raw replies expire on schedule; stalled runs are stopped; webhook retries happen.
- **Reproduction:** an empty database, then `npm run migrate`: 44 applied, the `cron` schema absent, 0 jobs. An empty database with `create extension pg_cron` first, then `migrate`: 3 jobs.
- **Expected:** a deployment without the jobs is detected before launch.
- **Minimal fix:**
  - A free `npm run verify:cron`. It checks every required job by name, schedule, active flag and last result. It says "pg_cron not installed (local stack)" distinctly from "job missing", and exits non-zero on a missing job.
  - The migrations stay tolerant, so local stacks still build, but they `raise notice` when they skip.
- **Regression test:** `verify:cron` on both fresh databases.
- **External configuration:** Supabase dashboard → Database → Extensions → enable `pg_cron`, `pg_net` and `vault`; then `npm run migrate`, `npm run schedules:clock -- install`, `npm run verify:cron`.

## Product gaps

### G1 · Medium · No idempotency on `POST /api/v1/runs`

- **Behaviour CONFIRMED:** `harness/idem.mts`: the same request sent twice with `Idempotency-Key: release-2026-10-01` answered 201 twice and stored 2 runs.
- **Impact:** a CI retry after a network timeout starts, and spends, a second run (a trial run, or the customer's key). With C7 it is not even capped.
- **Fix:**
  1. Migration: `run_requests (workspace_id, key, request_hash, run_id, created_at)` with a unique `(workspace_id, key)`, RLS on, a path in `erase_workspace()`, and expiry after 24 h in the daily pass.
  2. The same key and body return the original run with 200. The same key with a different body returns 409.
  3. Authorisation and the entitlement check still run first.
  4. The CLI and the n8n templates send a stable key per intended run.
- **Test:** 20 concurrent identical POSTs → 1 run; the replay → 200 with the same id; a different body → 409.

### G5 · Decision · Is an uncorroborated verdict a pass?

- **Where:** when the second model cannot be reached, `src/lib/judge/consensus.ts:115-124` returns the first model's verdict with `agreement: "unconfirmed"`. `src/lib/report/ci.ts:42-70` and the webhook then count it as a pass. Reports already label it ("uncorroborated: N").
- **Conflict:** your invariant list says "error / unexecuted / unable-to-verify / uncorroborated are not passes". The product's current, documented rule is "One model is reported as not corroborated", meaning a labelled verdict.
- **Options:**
  - **(a)** Keep it as a labelled pass.
  - **(b)** The pipeline outcome treats `unconfirmed` as `incomplete` (CI exit 2) while the letter stays.
  - **(c)** `unconfirmed` becomes no-result.

  (b) is the smallest change that makes the invariant true for automation. It must be gated on the payload format: changing `ciOutcome` for format ≤ 12 would change the exit code of reports already in clients' hands. **Your decision.**

### G6 · Decision · Raw replies through `?include=responses`

- **Where:** `src/lib/api/read.ts:103-166`.
- **What it does today:**
  - any key with `read` gets raw replies, transcripts and inputs, unredacted, including key-shaped strings (canary, 2026-09-30 and today);
  - the response is `no-store`, and expired raw evidence reads `raw_expired_at`;
  - no separate scope, no audit row, no redaction.
- **Compatible with:** "no key or raw response in reports" (reports scrub, and this is not a report).
- **Weak against:**
  - least privilege, because a CI key that only gates releases does not need customer conversations;
  - agency sharing, because a read key handed to a client also hands over raw transcripts.
- **Proposed:**
  - a separate `responses` scope (existing keys keep access until rotated, so nothing breaks);
  - an `api_key_reads` audit row per raw read;
  - a `redacted=true` default with `raw=true` opt-in.

  A customer-facing API change: **your approval**.

### G7 · Pass/fail/incomplete is decided in four places

- `ciOutcome(payload)` (`src/lib/report/ci.ts:42`), used by the CLI and the JSON and JUnit exports, reads sealed counts and the band.
- `runEventBody` (`src/lib/webhooks/deliver.ts:150`) reads stored rows.
- The n8n release gate recomputes from `counts` (`public/examples/n8n-novera-release-gate.json:285-345`).
- Any API consumer must do the same, because `GET /api/v1/runs/<id>` returns counts but no outcome and no planned count.

They agree for every state the runner produces (verified 2026-09-30 and today), and disagree on R2's planted state.

**Fix:**
1. One pure `outcomeFromStoredRun(snapshot)`, with `planned` from the manifest.
2. The webhook, `GET /api/v1/runs/<id>` (a new `outcome` and `planned` field), MCP and the n8n gate read it.
3. The CLI keeps reading the sealed payload, which already carries `planned`.
4. A property test asserts webhook = API = CI over every legal combination.

### G4 · Low · Soft 404s

- **Behaviour CONFIRMED** (`harness/routes.mts`, signed in as workspace A):
  - `/runs/<B's run>`, `/runs/<zero uuid>`, `/runs/not-a-uuid`, `/agents/<B's agent>` and `/agents/<zero uuid>` all answer **200** with "Nothing here" and no B content;
  - `/no-such-route` answers 404.
- **Cause:** `notFound()` inside a streamed page (Next 16 sends the status before the page decides).

- **Fix:** resolve the run or agent before streaming, in the page's own non-streamed segment or in `proxy.ts` for UUID shape, so the 404 status is sent. Only if measured to work in Next 16; otherwise accept it and document.
